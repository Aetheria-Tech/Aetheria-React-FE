# Aetheria FE Style Guide 초안

Aetheria React Frontend를 구현하면서 지키는 코드 작성 원칙과 아키텍처 분리 기준을 정리했습니다.  
목적은 새 기능을 추가하거나 코드 리뷰를 받을 때, “어떤 기준으로 작성했는지”를 명확히 공유하는 것입니다.

## 1. 핵심 개발 원칙

- 기존 기능 유지를 최우선으로 한다.
- 변경 범위는 작업 목표에 필요한 최소 범위로 제한한다.
- Swagger와 실제 백엔드 구현을 API 계약의 기준으로 삼는다.
- 백엔드에 없는 endpoint나 응답 필드는 프론트에서 추측해서 만들지 않는다.
- 프론트와 백엔드 동작이 다르면 백엔드를 임의로 수정하지 않고 확인 필요 항목으로 분리한다.
- UI 문구는 한국어 사용자 흐름을 기준으로 자연스럽게 작성한다.
- 테스트를 삭제하지 않는다. 동작 변경이 있으면 관련 테스트를 추가하거나 갱신한다.
- 대규모 리팩터링은 기능 구현과 분리한다.

## 2. 모듈 분리 기준

### pages
라우트 단위 화면 컴포넌트를 둔다.

- URL 파라미터, 페이지 단위 상태, 화면 전환을 담당한다.
- 서비스 호출 결과를 화면 흐름에 맞게 조합한다.
- API 요청 상세 구현은 직접 흩뿌리지 않는다.

### components
재사용 가능한 UI 컴포넌트를 둔다.

- props 기반으로 동작하게 만든다.
- 라우팅, 인증, API 호출 같은 앱 전역 흐름은 최소화한다.
- 지도, 썸네일, 보호 라우트처럼 재사용 가능한 UI를 관리한다.

### components/ui
버튼, 입력, 라벨, 셀렉트 같은 작은 UI primitive를 둔다.

- 도메인 로직을 넣지 않는다.
- 스타일 일관성을 유지하는 역할에 집중한다.

### services
외부 시스템과의 통신 및 브라우저 저장소 접근을 담당한다.

- API 호출, 인증 세션, 토큰 저장소, SSE 구독, localStorage task tracking을 관리한다.
- React hook이나 JSX를 사용하지 않는다.
- 응답 구조를 프론트 타입으로 매핑한다.
- 백엔드 계약 변경이 필요한 부분은 코드로 추측하지 않고 확인 필요로 남긴다.

### hooks
React 상태와 서비스 호출을 조합하는 재사용 hook을 둔다.

- 로딩, 에러, 데이터 갱신 흐름을 캡슐화한다.
- API 호출 자체의 세부 구현은 services에 둔다.

### context
전역 상태를 둔다.

- 인증 사용자, 토스트처럼 앱 전체에서 공유되는 상태만 관리한다.
- 페이지 전용 상태를 context로 올리지 않는다.

### lib
순수 유틸리티 함수를 둔다.

- 날짜/거리 포맷팅, 좌표 계산, polyline 처리, 런타임 판별처럼 React에 의존하지 않는 로직을 둔다.
- 사이드 이펙트를 최소화한다.

### types
공유 타입을 둔다.

- API 응답 타입, 도메인 타입, 외부 라이브러리 보강 타입을 관리한다.
- 서비스와 페이지가 같은 계약을 바라보게 만든다.

## 3. API 연동 원칙

- API 요청은 services 계층에서 관리한다.
- 공통 HTTP 설정은 api-client를 통해 처리한다.
- 서버 응답 래핑은 unwrapApiResponse 같은 공통 유틸을 사용한다.
- 인증 재발급, access token 조회, refresh cookie 전송은 auth-session과 auth-service의 책임으로 둔다.
- 페이지 컴포넌트는 endpoint 문자열을 직접 많이 알지 않게 한다.
- Swagger와 실제 백엔드가 다르면 실제 백엔드 구현을 확인하고, 불일치 사항은 확인 필요로 기록한다.

## 4. 비동기 러닝아트 생성 흐름 원칙

비동기 생성 기능은 task 기반 흐름으로 관리한다.

- 생성 요청 성공 시 taskId를 받는다.
- /mypage/tasks/:taskId 생성 상태 페이지로 이동한다.
- 생성 상태 페이지는 SSE를 우선 구독한다.
- SSE 연결 실패, 미지원, 지연 시 polling fallback을 사용한다.
- 완료 시 생성된 러닝아트 ID로 상세 페이지(/mypage/:id)로 이동한다.
- 실패 시 실패 UI와 오류 메시지를 보여준다.
- 새로고침하거나 나중에 마이페이지에 들어와도 localStorage 기반으로 상태를 다시 확인할 수 있어야 한다.

## 5. SSE / Polling 원칙

### SSE
- 실제 백엔드에 존재하는 SSE endpoint만 사용한다.
- task 단위 구독을 기준으로 한다.
- 연결 종료, 페이지 이탈, 라우트 변경 시 구독을 정리한다.
- CONNECTED, COMPLETED, FAILED 이벤트를 명시적으로 처리한다.
- 최신 백엔드 규격 기준 COMPLETED.data는 생성된 러닝아트 ID 문자열이다.
- SSE data가 유효하지 않으면 상태 조회 API로 fallback한다.

### Polling
- setInterval 대신 재귀 setTimeout을 사용한다.
- 이전 요청이 끝난 뒤 다음 요청을 예약해 요청 중첩을 막는다.
- 완료/실패/페이지 이탈 시 polling을 중지한다.
- 일시 실패는 사용자에게 즉시 실패로 확정하지 않고 제한적으로 재시도한다.

## 6. React 상태 관리 원칙

- setState updater 함수 내부에서는 localStorage 변경, ref 변경, navigate 같은 사이드 이펙트를 수행하지 않는다.
- 비동기 callback에서 오래된 task나 route 상태를 덮어쓰지 않도록 ref guard를 사용한다.
- route parameter가 바뀌면 관련 state와 ref를 초기화한다.
- 페이지 이탈 시 SSE, timeout, polling을 정리한다.
- 완료 이동은 중복 navigate를 막기 위해 navigateOnceRef 같은 guard를 둔다.
- 화면 이동 직전에도 기존 정보를 유지해 깜빡임을 줄인다.

## 7. UI 작성 원칙

- TailwindCSS를 기본 스타일링 방식으로 사용한다.
- 공통 브랜드 색상은 Tailwind config의 token을 우선 사용한다.
- Radix UI primitive와 기존 components/ui 컴포넌트를 우선 재사용한다.
- loading, empty, error, failed 상태를 명확히 구분한다.
- 사용자가 기다려야 하는 화면에는 상태 문구와 가벼운 애니메이션을 제공한다.
- 버튼, 링크, 카드 클릭 동작은 사용자가 예상 가능한 경로로 연결한다.
- UI 전면 리메이크는 기능 작업과 분리한다.

## 8. TypeScript 원칙

- API 응답은 명시적인 타입으로 매핑한다.
- unknown 데이터는 검증 후 사용한다.
- 불필요한 any 사용을 피한다.
- 문자열 status 값은 union type으로 관리한다.
- 중복되는 기본값은 상수로 분리한다.

## 9. 테스트 원칙

주요 검증 대상은 다음과 같다.

- 생성 요청 성공 후 생성 상태 페이지 이동
- SSE 구독 시작 및 cleanup
- polling fallback 시작 및 중지
- 완료 시 상세 페이지 자동 이동
- 실패 시 실패 UI 표시
- 마이페이지에서 생성 중/완료/실패 상태 표시
- 인증 상태와 보호 라우트 동작
- API 응답 매핑과 fallback 처리

검증 명령은 기본적으로 아래를 사용한다.

```bash
npm run lint
npx jest --runInBand
npm run build
```

## 10. 클린 코드 원칙

- 함수는 하나의 책임만 가진다
- UI, 상태, API 로직을 한 파일에 과하게 섞지 않는다
- 중복되는 문자열, 기본값, 상태 판별 로직은 상수 또는 helper로 분리한다
- 조건문이 길어지면 의미 있는 이름의 함수로 분리한다

규칙:
- Side Effect가 있는 로직과 Pure Function을 명확히 구분한다
- 로컬스토리지, 네트워크 요청, 라우팅 변경은 호출 위치가 명확해야 한다
- 코드만으로 의도가 드러나지 않는 경우에만 최소한의 주석을 작성한다
- 미래 확장을 이유로 불필요한 추상화를 만들지 않는다

## 11. 코드 리뷰 대응

우선순위:

- high: 반드시 확인하고 수정한다
- medium:
  - 실제 버그, UX 문제, 데이터 유실, 백엔드 계약 위반 → 수정
  - 구조 개선, 확장성 제안 → 근거를 남기고 보류 가능

대응 방식:

- 수정 여부와 판단 근거를 명확히 남긴다
- 수정한 경우 어떤 방식으로 변경했는지 기록한다
- 관련 검증 방법(lint, test, build 등)을 함께 작성한다
- 이미 코드에서 처리된 항목은 변경 없이 설명으로 대응한다

---

## 12. 하지 않는 것

- 백엔드 코드를 프론트 작업 중 임의로 수정하지 않는다
- Swagger 및 백엔드에 없는 endpoint를 프론트에서 가정하지 않는다
- 인증 구조를 기능 작업 중 임의로 변경하지 않는다
- 테스트를 삭제해서 통과시키지 않는다
- 파일 이동이나 대규모 리팩터링을 기능 구현과 함께 진행하지 않는다
- UI 전체 스타일을 작업 범위를 벗어나 변경하지 않는다
